# Как продемонстрировать проект

Время показа: 7–10 минут. Нужен Node.js 20+ и интернет (данные MEXC и библиотека графиков с unpkg).

## 0. Подготовка (за 20–30 минут до показа)
```bash
cp .env.example .env      # MongoDB необязательна — без неё история хранится в памяти
npm install
npm start
```
Откройте `http://localhost:10000` и оставьте вкладку открытой. История индикатора BID/ASK накапливается
только пока сервер работает (биржа отдаёт лишь текущий стакан, прошлое восстановить нельзя). Сервер пишет
BTC/ETH/SOL и все просмотренные пары в фоне раз в 15 с, поэтому за 20–30 минут линии успеют заполниться.
Перед показом на 1m-таймфрейме откройте символы, которые собираетесь показывать.

## 1. Сценарий показа
1. **Терминал** (`/`) — свечи, объём, стакан, метрики BID / ASK / Imbalance, поиск пары, таймфреймы.
   Переключите 1m → 5m → 15m: индикатор перестраивается из истории (в логе внизу видно «История индикатора: N точек (memory|mongodb)»).
2. **Индикатор на истории** — линии BID/ASK идут на всём отрезке накопленной истории, а не только «от момента открытия страницы».
   Закройте вкладку, откройте снова — история на месте (после перезапуска сервера: при MongoDB — на месте, без неё — копится заново).
   **Индикаторы** — кнопка «ƒ Индикаторы» в шапке: включите EMA 20, RSI 14 и MACD (RSI/MACD открываются отдельными панелями под BID/ASK, все графики листаются синхронно).
   Переключите на **1D** и включите «Rinar: уровни и дивергенция» — на 1m–4H этот пункт заблокирован, потому что формулы Rinar рассчитаны на дневные свечи.
3. **Сканер** (`/scanner`) — топ USDT-пар по обороту, глубина 2/5/…%, фильтры по Imbalance, клик по паре открывает терминал.
4. **Swagger** (`/api-docs`) — выполните «Try it out»: `GET /api/health`, `GET /api/data?symbol=BTCUSDT`,
   `GET /api/history?symbol=BTCUSDT&bucket=60` (смотрите заголовок `X-History-Source`), `GET /api/indicators?symbol=BTCUSDT&interval=1d&names=rsi14,rinar`, ошибку: `GET /api/data?depth=99` → 400.
   Сырой JSON: `/openapi.json`.
5. **Состояние хранилища** — `GET /api/health`: `history.store` (`mongodb`/`memory`), число точек, список пар, которые пишутся в фоне.
6. **Автотесты** — отдельный сценарий на 5 минут: раздел «3. Как показать автотесты».

## 2. Автотесты (122 теста, ~3 секунды)
`npm test` запускает все файлы из `tests/` встроенным раннером Node (`node --test`), без новых зависимостей. MongoDB и интернет не нужны:
биржа подменяется фикстурами, история идёт в память.

| Файл | Что проверяет |
|---|---|
| `validation.test.js` | парсинг символа и числовых параметров, границы, коды 400 |
| `mexc.service.test.js` | расчёт ликвидности (граничные случаи), ошибки биржи: сеть → 502, тайм-аут → 504 |
| `history.store.test.js` | корзины (bucket), кольцевой буфер, фильтр `since`, «самые новые N точек» |
| `history.service.test.js` | троттлинг записи, фолбэк БД → память, наблюдаемые пары, TTL, prune |
| `market.service.test.js` | список символов, `getMarketData` + запись истории, сканер, фоновый логгер |
| `indicators.test.js` | формулы индикаторов против эталона `rinar_bot` (Rinar, DEMA ATR, RSI, MACD, Bollinger, дивергенция) + свойства (границы RSI, порядок зон, окна SMA/EMA) |
| `indicator.service.test.js` | каталог, проверка совместимости с таймфреймом, `parseCandles`, обрезка до `limit`, запрос 500 свечей у MEXC |
| `indicators.controller.test.js` | разбор параметров `/api/indicators` и `/api/klines` (коды 400/502, `1h` → `60m`) без Express |
| `terminal.indicators.test.js` | скрипт терминала в Node с заглушками DOM и графиков: меню, оверлеи, панели RSI/MACD, блокировка Rinar вне 1D, синхронизация осей |
| `templates.static.test.js` | EJS: id из скриптов есть в разметке, include навигации, все `/api/*` из страниц описаны в Swagger |
| `swagger.spec.test.js` | OpenAPI ↔ реальные маршруты, все `$ref`, границы параметров совпадают с валидацией |
| `api.http.test.js` | все REST-эндпоинты (включая `/api/indicators`) на настоящем Express, обработка ошибок, 404 |
| `smoke.script.test.js` | сама пост-деплойная проверка `scripts/smoke.js`: проходит на здоровом сервере, падает при сбое биржи/недоступном сервере, коды выхода CLI |
| `pages.http.test.js` | рендер `/`, `/scanner` (+алиасы), подсветка навигации, статика, `/openapi.json`, Swagger UI |

## 3. Как показать автотесты (5 минут)
Нужны только Node.js 20+ и `npm install`. MongoDB и интернет не требуются.

1. **Всё зелёное за 3 секунды.** `npm run test:spec` — построчный отчёт: 122 теста, ни один не упал. Покажите, что названия тестов читаются как требования («троттлинг: чаще интервала запись пропускается», «1H → 60m» и т. д.).
2. **Тесты ловят баги.** `npm run demo:break` — скрипт копирует проект во временную папку, вносит туда 4 реалистичных бага (неверная глубина стакана, выключенный троттлинг истории, ошибка в формуле RSI, сломанная валидация) и запускает тесты: каждый баг должен быть пойман. Ваши исходники при этом не меняются. Это главный аргумент, что тестам можно доверять. Можно показать один баг: `npm run demo:break -- 3`.
3. **Формулы против оригинала.** Откройте `tests/fixtures/rinar-golden.json` и `gen_golden.py`: эталон посчитан Python-кодом `rinar_bot` на 450 свечах, JS-реализация совпадает с ним с точностью ~1e-12.
4. **Покрытие.** `npm run test:coverage` — таблица покрытия по файлам.
5. **Проверка работающего сервера.** В одном окне `npm start`, в другом `npm run test:smoke` — 9 проверок живого экземпляра по HTTP (health, страницы, Swagger, валидация, 404). Для боевого сервера: `npm run test:smoke -- https://ваш-домен`. С реальной биржей: `npm run test:smoke:live` (ещё 7 проверок: пары, стакан, свечи 1h → `60m`, индикаторы, история, сканер).
6. **CI.** Файл `.github/workflows/test.yml`: при каждом push GitHub сам ставит зависимости, гоняет тесты на Node 20 и 22, поднимает сервер и запускает smoke-проверку. Результат — зелёная галочка в репозитории и JUnit-отчёт во вложениях.

## 4. Тесты на сервере (деплой)
Тесты бывают трёх видов, и каждый запускается в своём месте:

| Что | Команда | Где и когда | Что нужно |
|---|---|---|---|
| Автотесты (122) | `npm test` / `npm run test:ci` | CI и/или шаг сборки на хостинге, до старта приложения | только Node.js |
| Smoke-проверка сервиса | `npm run test:smoke -- <URL>` | сразу после деплоя, против живого URL | URL сервера |
| Smoke с реальной биржей | `npm run test:smoke:live -- <URL>` | после деплоя и по расписанию (cron / «Scheduled workflow») | сервер имеет доступ к MEXC |

Код выхода: `0` — всё хорошо, `1` — есть упавшие проверки, `2` — сервер недоступен; это удобно для деплой-скриптов и мониторинга.

**Хостинг.** В настройках сборки (например, Render: *Build Command*) укажите `npm ci && npm test` — тогда версия с падающими тестами не выкатится. Для автоматической проверки после деплоя в GitHub Actions добавьте шаг `npm run test:smoke -- ${{ secrets.APP_URL }}`.

**Расписание.** Чтобы узнать о сбое раньше пользователей, запускайте `test:smoke:live` раз в час по cron или scheduled workflow: он поймает смену формата ответа MEXC, недоступность биржи и падение сервиса.

## 5. Что было не так с индикатором и что изменено
**Причины**
- Каждая загрузка `/api/data` (каждые 3 с на каждую открытую вкладку) писала документ в MongoDB → база быстро забивалась.
- На поле `timestamp` было два индекса (обычный и TTL) — конфликт, из-за которого TTL-очистка могла не создаваться.
- В фоне писались только BTC/ETH/SOL, и только при подключённой БД; для остальных пар история была с «дырами».
- `/api/history` с `limit` отдавал самые СТАРЫЕ точки, время корзины не совпадало со временем свечи.
- Без БД история была недоступна вовсе (503).

**Решение**
- Троттлинг: не чаще одной точки на пару за `HISTORY_MIN_INTERVAL_MS` (5 с), сколько бы вкладок ни было открыто.
- Жёсткий потолок `HISTORY_MAX_DOCS` + периодическая очистка самых старых записей + TTL 7 суток → размер БД ограничен (~100 МБ при значениях по умолчанию, оценка).
- Резервный кольцевой буфер в памяти: индикатор работает и без MongoDB, и при её сбое/переполнении квоты.
- Любая открытая пара автоматически попадает в фоновую запись (до `WATCH_MAX_SYMBOLS`, забывается через 24 ч без просмотров) — нет «дыр».
- В историю всегда пишется глубина 5 %, независимо от параметра `depth` запроса.
- Корзины выровнены по границе свечи, `limit` отдаёт самые новые точки, источник виден в `X-History-Source`.

**Ограничения (честно)**
- Историю до первого запуска сервера восстановить невозможно — API MEXC даёт только текущий стакан.
- Без MongoDB история живёт в памяти процесса и теряется при перезапуске.
- На хостингах с «засыпанием» (например, бесплатные тарифы) фоновая запись останавливается вместе с процессом.
